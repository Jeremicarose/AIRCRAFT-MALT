# CKB Receiver Registry Pilot Brand

This guide keeps the product, pilot page, funding request, and outreach messages
consistent. It does not create a new product name or expand the claims the
software can support.

## Name and promise

**Product:** CKB Receiver Registry

**Programme:** CKB Receiver Registry Operator Pilot

**Primary line:** Stable identity for independently operated receivers.

**Plain-language promise:** A receiver keeps one identity while its owner,
metadata, network, or lifecycle state changes. Coordinators can discover the
current record and inspect the ordered history.

Lead with the receiver problem. Introduce CKB as the mechanism that verifies the
authorized lifecycle, not as the reason someone should care.

## Audience messages

### Receiver owner or operator

Keep one identity when a receiver moves, changes owner, changes network, or is
retired. You approve every testnet change in your own wallet.

### Network coordinator or developer

Discover current receiver records, inspect owner-authorized history, and export
one documented format without relying on a private master spreadsheet.

### Sponsor or CKB community reviewer

Fund a bounded six-person study that tests whether CKB-backed receiver lifecycle
evidence solves a real coordination problem. The outcome may be continue,
change direction, or stop.

## Evidence boundary

Always say:

- CKB verifies the contract-valid identity, current owner authorization,
  sequence, and lifecycle transitions.
- Registry coordinates and capabilities are owner-declared metadata.
- Operational qualification separately checks feed identity, timing, freshness,
  and geometry.
- MLAT separately uses qualified observations to estimate an aircraft position.

Never say that the Registry proves physical hardware, location truth, feed
honesty, clock accuracy, observation truth, or live aircraft accuracy.

## Voice

- Precise, calm, and operational.
- Explain the receiver task before the blockchain implementation.
- State testnet, replay, simulation, saved evidence, and live state explicitly.
- Prefer concrete verbs: register, discover, update, transfer, revoke, inspect,
  export, qualify, correlate, estimate.
- Welcome negative evidence. Do not ask participants to validate the product.

Avoid speculative language such as revolutionary, trustless, immutable truth,
decentralized aviation, real-time proof, or production-ready.

## Visual system

Use the existing application system:

- graphite surfaces for operational context;
- cyan for Registry identity and verified lifecycle facts;
- blue for MLAT and navigation actions;
- green for confirmed passing states;
- yellow for incomplete or attention states;
- orange for replay or simulation;
- red only for failure or permanent revocation.

Use IBM Plex Sans for interface and programme copy. Use IBM Plex Mono only for
identities, hashes, and machine-readable values. Do not introduce crypto motifs,
coins, neon effects, or decorative blockchain imagery.

The approved diagrams are listed in [assets/README.md](assets/README.md). The
Registry/MLAT responsibility boundary should accompany any funding proposal or
participant invitation that discusses both systems.

## Status language

Use only these public recruitment states:

| State | Meaning |
|---|---|
| Programme preparation | Funding, readiness, or the private application form is incomplete |
| Interest list open | Expressions of interest are accepted, but sessions are not being promised |
| Applications open | Funding is confirmed, the readiness gate passed, and sessions can be scheduled |
| Applications closed | The current cohort is no longer accepting applications |

Never describe a proposed incentive as paid, funded, or guaranteed until the
money is reserved for the cohort.
